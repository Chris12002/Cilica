# DiffPlex v111: a measured path past the retained Unity player

2026-10-20. Production remains committed native v111, be9afab80f76051183576b8780954ad02b475752,
on codex/profile-v107. Apple M4 Pro ARM64, Apple Clang 17, C++20 O2/NDEBUG,
no C++ exceptions/RTTI. Ordinary .NET 10.0.11, not NativeAOT.

## Outcome and next implementation order

A generated-C++ experiment takes **23.722 us/character diff**, versus
**26.449 us for Unity IL2CPP** and **27.051 us for committed v111**, in the same
interleaved batch. That is **10.31% less execution time than this Unity player**
and **12.31% less than v111**. This is a prototype result, not a shipped compiler
improvement or a general claim of beating Unity. The compiler/library sources
remain unchanged; shared-module and full runtime regression acceptance still
belong to implementation.

Implement in separate measured/reviewed slices:

1. Expose allocation_room, allocation_safepoint, allocate_string and
   string_from_character bodies to optimized inlining. Preserve each helper's
   prior O0 policy and every allocation/observer/collection check. This is the
   strongest individual character-diff result: **4.91%** less time, **1.32%**
   on line diffs. Small common allocation helpers can be measured before adding
   the two string helpers if the implementation is split more finely.
2. Expose the checked frame-borrow resolution chain to optimized inlining.
   Keep token/cache collision checks, frame lifetime, extents, narrowing,
   readonly behavior and reference validation. Measured **2.62% / 1.84%** gains
   for character/line diffs. No additional methods become typed-kernel eligible.
3. Consolidate array-location construction checks already performed earlier in
   that same helper. Retain kind-specific slot/component checks before returning
   the location. General location resolution stays checked. Measured **2.49%**
   on character diffs, effectively unchanged on line diffs.
4. Remove the redundant initial clearing of collector scratch and clear live
   survivors while sweeping. All allocations and every exit must establish clean
   marks; failed/report-only traversals retain cleanup. Inventory validation,
   checked membership, limits and reporting order remain. Measured **2.69% / 3.16%**
   individually. This needs the broadest invariant review and comes last.

These are runtime/compiler operation families; no DiffPlex method or workload
name is used to select the combined changes. Percentages from separate batches
must not be added. The combined executable grows from 568,360 to 599,432 bytes
(5.47%); maximum native frame size in the release timing binary stays 432 bytes.

## Fresh comparison with Unity

The existing Unity 6000.3.2f1 ARM64 player was retimed, without rebuilding.
Its settings record IL2CPP Release/OptimizeSpeed, Minimal stripping, incremental
GC enabled, and no development build. The input plugin hash matches the exact
DiffPlex DLL, and GameAssembly.dylib matches the original captured build hash.
The backup managed DLL is stripped and has a different hash; it is not treated
as the original input. Unity, .NET and v111 match all 523 observations/checksum
6146 before timing. Unity launches through macOS LaunchServices and exits after
the bounded harness. Only the loop inside the player is timed, excluding startup.

| Character workload | Median us/diff | Ratio to .NET | Ratio to Unity |
| --- | ---: | ---: | ---: |
| Committed Cilica v111 | 27.051 | 4.94x | 1.023x |
| Combined experiment | 23.722 | 4.34x | 0.897x |
| Unity IL2CPP | 26.449 | 4.83x | 1.000x |
| Ordinary .NET | 5.472 | 1.00x | 0.207x |

Three processes per variant, seven samples per process. Native uses 1,024 diffs
per sample, Unity 4,096, .NET 16,384. Each process warms for at least 300 ms.
.NET tiering and ReadyToRun are disabled. Order is rotated/reversed; every timed
sample verifies its checksum. Builds, profiling, instrumentation and sanitizer
runs do not overlap release timing. Process medians and all samples are retained.
These are local process batches, not independent machines or confidence intervals.

The earlier fresh batch had v111 27.011 us, Unity 26.232 us and .NET 5.485 us.
The older retained Unity result was 24.368 us. Use the refreshed paired comparison
above, while recognizing Unity's run-to-run variation; a production claim needs
fresh post-implementation measurements and more workloads/platforms.

## Controlled experiments

Every listed variant matches 523 character and 2,061 line observations against
.NET, with checksums 6146 and 3122 respectively. These release correctness checks
are not full compiler/runtime acceptance. Only the selected combined experiment
also received the sanitizer/constrained-stack/invariant checks described below.

| Generated-code experiment | Character time reduction | Line time reduction |
| --- | ---: | ---: |
| Checked frame-borrow chain inlining | 2.62% | 1.84% |
| Array-borrow helper inlining alone | -1.74% | 0.23% |
| String/character allocator inlining alone | 1.90% | 0.44% |
| Clear survivors during sweep only | -0.56% | 0.59% |
| Remove initial clear plus clear survivors in sweep | 2.69% | 3.16% |
| Alternate collector address hash | -2.38% | 0.83% |
| Alternate descriptor address hash | -1.41% | -0.68% |
| Consolidated array-location construction validation | 2.49% | 0.00% |
| Common allocation helper inlining | 2.80% | 1.29% |
| Common allocation plus string helper inlining | 4.91% | 1.32% |
| Combined four selected families, first batch | 12.82% | 5.05% |

Negative reductions mean slower. Do not adopt the alternate hashes or blanket
array-helper inlining from these results. A later variant forced inlining of all
34 existing typed wrappers with no Location parameters, selected structurally
from the existing kernel proof. It saved 0.30% on characters and 5.67% on lines;
adding it to the combination saved 12.23% / 8.26% from baseline in that batch.
It was not included in the Unity comparison or sanitizer acceptance and is not
part of the selected four-family recommendation.

Native disassembly confirms the allocation mechanism: v111 has 21 named direct
calls to allocation_room, 19 to allocation_safepoint, seven to allocate_string
and two to string_from_character. The allocation-inlining variant has zero
such calls. Checks and cold collector calls remain. Counts cover direct bl call
sites, not dynamic executions, tail branches or folded symbol aliases.

## Broader workload exposes a different library cost

The existing pinned DLL already supports a 1,024-character line workload in
addition to the 128-character character workload. Both .NET and native outputs
match all 2,061 line observations. This adds workload variety without changing
the input DLL, but is still one library; it does not establish broad performance.
The current Unity harness selects only character diffs, so no Unity line result
is claimed.

Final line medians: **69.373 us v111 -> 66.815 us combined experiment**, a **3.69%**
reduction, versus **6.961 us .NET**. The experiment's line improvement ranges
3.69–5.63% across batches; its remaining .NET gap is about 9.60x. This is why the
character result cannot stand in for general execution performance.

Two line profiles contain 5,054 exclusive samples. MatchStringSeparator has
1,516 (30.00%), CopySubstring 378 (7.48%), and Split itself 260 (5.14%). These
are stronger line-specific targets than further tuning character allocation.

The owned String.Split performs one separator scan to count output pieces, then
rescans to populate them. .NET and Unity instead retain separator positions and
widths. Cilica's CopySubstring also allocates an intermediate Int32 array before
constructing UTF-16 text. A bounded separator-position buffer and direct rooted
substring construction are the next library investigations, after the selected
runtime slices. They need measurement and checks for separator precedence,
empty/whitespace/trim behavior, identity, allocation failure and rooting; no gain
or implementation is claimed yet. These would benefit all callers of those APIs.

## Roslyn and IL2CPP evidence

Actual Release IL remains authoritative. Input PDB records C# 14.0 Release/AnyCPU
and Roslyn 5.9.0-1.26379.115+14fbf8d5271c98133561eb55185fdb05b286f578.
The inspected Roslyn checkout is a retained reference revision, not an exact
source match; its revision and source hashes are recorded. No such match is claimed.

BuildModificationData uses ldelema Int32 at IL_001e and IL_0053 before Int32.Equals
at IL_002c and IL_0063. Roslyn EmitArrayElementAddress emits ldelema with the
required readonly/type handling. Unity's matching method uses checked inline
GetAddressAt and an ordinary Int32 pointer. Cilica constructs and validates a
Location carrier, then validates it again at use. Consolidating duplicate checks
inside construction is narrower than trusting later uses or removing lifetime
validation. No reads are moved across argument evaluation or managed calls.

Roslyn EmitObjectCreationExpression emits newobj after argument evaluation; it
does not prescribe Cilica's allocation budget/observer helpers. Unity String::NewSize
uses one pointer-free allocation with in-object UTF-16 storage. The proposed
inlining exposes Cilica's own fast-path conditions to Clang without changing its
pool, identity, roots, managed quota or fallback collection policy.

LineChunker.Chunk has String.Split at IL_0008. The owned core's MatchStringSeparator
is token 060002e4; CopySubstring is 060002d8, and the relevant Split is 060002e3.
Retained core metadata/REA records are reused only after checking the fresh core
hash. .NET MakeSeparatorListAny and Unity's generated MakeSeparatorList append
positions and lengths into ValueListBuilder buffers rather than rescan when
materializing output. Roslyn is not the source of this library algorithm difference.
Line-addressed excerpts and exact hashes are retained alongside the measurements.

## Validation, review and remaining gates

The combined experiment passes both complete transcripts in release and two
O1 ASan/UBSan builds with forced collection, internal/borrow diagnostics off/on.
Each requests a 512 KiB pthread stack and checks the actual 512–576 KiB size.
Maximum native frames in these extended acceptance harnesses are 544 bytes
release, 448 bytes diagnostics-off sanitized and 480 bytes diagnostics-on sanitized.
The timing binaries retain a 432-byte maximum. No sanitizer diagnostics occur.

Each acceptance run also performs 32 collector scenarios covering stopped
reporting, edge/object limits, invalid roots, invalid inventory owner, busy nested
collection during reporting, surviving and unreachable objects, empty collection,
mark/link cleanup and membership-index deactivation. These are reduced tests,
not a substitute for all existing tracing/collection and allocation-failure tests.

Production gates remain: preserve each helper's O0 policy; validate shared-module
linkage/function identity, allocation-failure and observer paths, malformed scalar/
reference/value-array locations, stale carriers and readonly/alias behavior; and
run full focused collector exit/scratch-failure tests before removing the clear pass.
Review of the experiments found no observed correctness failure, but those gates
prevent treating the generated-code prototype as an accepted compiler release.
