# DiffPlex ownership-validation fingerprint, 2026-10-08

The dominant measured problem is repeated linear ownership lookup, especially
inside pre-allocation root validation. An exact-membership index experiment in
generated C++ changes this workload's accepted median from **260.42 ms to 513.73 µs**
per diff, **507× faster**. It remains about **91× slower than .NET's 5.648 µs**.
This is a disposable experiment, not a production optimization or a general speed claim.
The [completed adoption review and residual profile](ownership-index-review.md)
recommend **not adopting the experiment as written**: a reproduced ownership
corruption mismatch and native stack-budget violation remain.

The original [b83954f report](../compatibility-candidates/diffplex-performance-20261008.md)
and its evidence are unchanged. Its roughly 46,000× ratio is numerically credible
for that workload. Its seven native samples mixed different heap phases; their
90–458 ms spread is substantially explained by garbage-dependent validation cost,
not a growing live leak or expensive collection pauses. Larger batches here narrow
that spread. The unverified 1,024-character line workload is still unmeasured.

## Ranked evidence

All time shares in this section are **instrumented**, excluding the initial cold
operation. Counters group ownership work under ordinary execution, `valid_roots`,
and `collect`. Only the latter two scopes read a clock; individual ownership queries
do not. Instrumentation can perturb code generation and time; clean timings below
come from separate binaries.

1. **Pre-allocation validation: 89.697% of 4.117 s across 19 warmed operations.**
   Each operation invokes `valid_roots` 824 times and performs 125,296 ownership
   queries there, including null queries. These walk 970,434,205 list nodes in total,
   about 51.1 million per operation on average. Root validation ranges from 74.0%
   to 93.3% of warmed sample time. Runtime source: `ObjectCppRuntime.cs`,
   `Instance::owns`, `valid_roots` and the string/object/array allocation paths.
   Every published frame slot is visited; a non-null slot searches the allocation
   list from its head. Long-lived input/cache references become expensive to find.
   Confidence: high; counters, source, isolated reducer and clean experiment agree.

2. **Ordinary reference checks: another 22,750 queries per warmed operation.**
   These walk 195,955,226 nodes across the same 19 operations, 16.78% of all measured
   list-node visits. Emitted array/field checks and runtime reference validation
   reuse `owns`. Their independent wall-time share is not measured: the 10.19%
   outside root validation/GC also includes all useful computation and profiling
   overhead. The index experiment changes lookup for both first and second findings.
   Affected features include managed array accesses, field access and typed calls.

3. **Allocation volume and heap phase amplify lookup cost.** Non-collecting warmed
   samples add exactly 824 objects and 85,928 charged bytes per diff. Eight separate
   explicit post-operation collections leave exactly eight objects and 5,488 bytes.
   Collection-after-each is an instrumented diagnostic, not the clean timing policy.
   It reduces the heap-dependent effect but still spends about 20 ms per diff.
   Normal collection is triggered near the 4,096-object bound, below the 1 MiB byte
   bound. Four measured collections cost 4.71 ms total, **0.114%** of instrumented
   elapsed time. Do not prioritize a collector rewrite from these results.

The standalone `micro` reducer constructs inventories of 1, 64, 512, 2,048 and
4,096 objects, issues 32,768 exact-member queries, then removes members and checks
null, invalid-address and foreign-object behavior. At 4,096 objects, median cost is
2,012 ns/query for list search versus 1.376 ns/query for the experiment. At one
object the index is slightly slower. These synthetic contiguous objects have
different cache locality from DiffPlex; use this as mechanism evidence, not a
prediction of whole-program speed. Results are retained for every size/repetition.

## Clean comparison and methodology

| Measurement | Baseline native | Experimental index | Normal .NET |
| --- | ---: | ---: | ---: |
| Median compute per diff | 260.420 ms | 513.733 µs | 5.648 µs |
| Range of 14 accepted samples | 211.771–274.575 ms | 493.190–534.365 µs | 5.570–5.850 µs |
| Iterations per sample | 16 | 16 | 32,768 |
| Median cold first call | 33.869 ms | 612 µs | 4.721 ms |
| Median no-op process command | 0.873 ms | 1.602 ms | 44.802 ms |
| Median cold end-to-end command | 34.813 ms | 1.286 ms | 182.248 ms |
| Measurement process RSS range | 12,340–12,468 KiB | 12,340–12,468 KiB | 38,628–38,764 KiB |

Three fresh processes per runtime each supplied seven samples. Host-load review
found an active dotnet process at 92.18 seconds, overlapping the final repetition.
All 21 samples remain raw evidence, but the **entire third repetition is excluded**
from the accepted comparison. The first two complete in 64.45 seconds of recorded
child-command wall time, before the observed competing build. Their alternating
runtime order supplies 14 accepted samples per runtime. The original all-data
506× estimate becomes 507×; this is a documented filtering correction, not a rerun.
Both native variants use equal batch counts, covering
multiple allocation/collection cycles per sample. The original 300 ms warmup rule
is preserved: accepted baseline processes warm eight operations (about 1.45 s),
index warms 592, and .NET warms 46,400–53,704. Starting heap phase therefore differs;
this is not an identical-heap microcomparison. Accepted baseline process medians
are 260.26–260.58 ms; index process medians are 503.69–522.42 µs.
Index batches last about 8 ms; a future
stable regression baseline should lengthen those windows and repeat across machines.

Input strings, two substitutions, root and checksum are unchanged. The full 523-value
transcript is compared between current .NET, index native and the immutable original
oracle. Every timed batch checks its accumulated checksum. Input construction,
compilation, JIT warmup and serialization stay outside steady compute. Native timing
uses `steady_clock` nanoseconds; .NET uses `Stopwatch.GetElapsedTime.TotalNanoseconds`;
each total is divided by its recorded iteration count. One direct root call encloses
each managed batch. No bridge, compilation or full-result traversal is hidden inside.

Cold first-call timing includes initialization (and .NET JIT). New no-op commands
print the same `0` result without the workload, providing a host-process baseline;
they still include process launch, host startup, output and teardown. Do not subtract
these noisy independent measurements to claim pure runtime startup. Full cold host
output still differs (printf versus JSON serialization). The index no-op median
exceeding its cold-command median illustrates the limits of these tiny samples.

RSS uses Linux `wait4` KiB for every child and includes code, warmup and the full
process lifetime. Current native charged heap bytes, post-GC survivors, RSS and
.NET allocated bytes are distinct quantities. .NET reports about 14,226 bytes/diff;
native reports 85,928 charged allocation bytes/diff with different representation
and accounting. The index adds **64 KiB per Instance**, not included in `heap.bytes`.
No native managed allocation quota was raised, but this extra memory requires an
explicit production accounting decision.

The compatibility lane confirmed quiescence. Review milestone 6 was sent the
requested window and release; it did not explicitly acknowledge the reservation.
Sampled host processes showed no active competing compiler during the accepted
first two repetitions; the late overlap is handled by the exclusion above.
The Docker cgroup accrued **zero new throttled periods/usec** during all uninstrumented
timing. The shared host still ran unrelated UI/system workloads; CPUs were quota
limited, not dedicated. These results are not a statistical confidence interval.

The experiment retains exact pointer equality before dereferencing unknown inputs.
Its 8,192-entry fixed open-addressed table is updated at all three validated
allocation publication sites and rebuilt after sweep. Full-table insertion falls
back to the original list search. The inventory remains the collector's source of
truth. The independent reducer checks removed/foreign/invalid pointers; all 523
observations also pass under ASan/UBSan with collection before every allocation,
including teardown/leak checks. This is focused experimental evidence, not the
full runtime corruption/conformance suite.

Before production: coordinate `ObjectCppRuntime.cs`/`ObjectCppMarking.cs` ownership,
decide index memory accounting, verify failure/reclamation/address-reuse behavior,
and preserve detection of privately forged/corrupted inventories at native and
diagnostic boundaries. Direct private list mutations can make an index stale; the
generated experiment covers runtime-owned publication/sweep paths only. Also cover
per-instance isolation, custom object limits, table saturation, allocation failure,
handles and caches. Do not replace membership tests with a blind `value->owner`
read or disable root validation. No production file, profile, limit or ABI changed.

The subsequent review **reproduced** the detached-root mismatch and stack-budget
failure; the risks above are now demonstrated adoption blockers, not only cautions.
See [the exact results and required gates](ownership-index-review.md).

The first attempt failed a transformation assertion because the synthetic reducer
added a fourth textual `++heap.count`. The correction matches the three exact
allocation-publication statements. Its failure logs remain retained; it produced
no accepted timing. A Docker copy into the read-only root was rejected; the bounded
owned sanitizer script was then supplied over stdin, without a host mount.
