# DiffPlex v104: allocator traffic, field access and local outputs

2026-10-20. Investigation at `742082a` (`codex/runtime-performance`), native v104.
Apple M4 Pro, macOS ARM64, Apple Clang 17, ordinary .NET 10.0.11.
No production compiler, library, runtime, quota or profile changes.

## Decision

Implement a **bounded, per-instance allocator for small string objects first**.
The experimental string-slot pool reduces total execution time by **12.80% and
12.92%** in two separately interleaved timing batches. Collection work, managed
object counts and managed byte charges are unchanged. This targets native
allocation/deallocation overhead without suppressing managed allocations or
changing live string identity.

Next, emit efficient field access where the actual generated layout is proven.
The inlined offset experiment saves **9.47%**; the production design must establish
C++ object/layout correctness rather than copying its raw byte-pointer arithmetic.
Direct local output borrows are a smaller, separately measured **3.84%** opportunity.
The combined experiment saves **27.24%**, but is diagnostic evidence, not a shipped
compiler improvement or a general correctness proof.

### Allocation experiment

The prototype acquires StringObject headers from per-instance slabs of 256 slots.
Collection returns unreachable slots to the instance's free list. Active objects
still join the ordinary managed inventory, retain distinct identities, preserve
string contents and are collected using the existing collector. Larger strings
retain their separately allocated character buffer. No string interning is added.

StringObject is 88 bytes. The warmed 256-diff run ends with 14 slabs, reserving
**315,504 bytes (308.1 KiB)**, with five slab acquisitions after warmup. The
prototype cap is 16 slabs / 4,096 slots / **360,576 bytes (352.1 KiB)**.
This is reserved native storage; occupied slots overlap live managed charges.
It must not simply be added to managed bytes to claim an RSS measurement.
RSS and cold-start effects were not measured.

Baseline and pool have exactly the same 21 collections, 7,329 cumulative live
observations, 78,687 cumulative dead observations, peak 4,096 inventory objects,
and 473,136 peak charged managed bytes. Live observations count an object again
if it survives multiple collections. These results isolate a useful allocator/
locality improvement without increasing the managed collection threshold.

### Field access experiment

Current field_address performs a descriptor lookup and an indirect call to a
typed accessor. The ARM64 helper itself is four instructions ending in `br x1`;
the caller also pays the call and loses optimization opportunities around it.
Dictionary.Find's kernel contains **11 static field-address call sites**.

Replacing the callback with a descriptor offset while keeping the helper out of
line saves only 2.50%. Allowing that offset computation to inline saves 9.47%.
Find's emitted native body falls from **716 to 572 bytes**, and its 11 helper
calls disappear. Thus the cost includes the optimization barrier, not just the
time attributed to the helper's four instructions.

The original out-of-line helper protects O0/sanitizer stack usage. A production
change should allow proven typed access in optimized code while preserving the
bounded fallback. It must cover exact dynamic layouts, inherited fields, alignment,
aliasing and C++ pointer provenance. The offset experiment's sanitizer pass does
not by itself prove those language-level requirements.

### Local output and array checks

The benchmark-only TryGetValue bridge keeps exact target selection, a staged
output scalar and the existing kernel. Kernel failure reconstructs a managed
location and uses the original call. Passing the local's storage directly avoids
location construction/resolution on the successful, non-allocating path.
Production needs a structural single-use/call-graph proof, alias rules and precise
fault/fallback ordering; matching benchmark tokens is only an experiment.

Omitting full array-shape checks at the typed Count/Get entries, while retaining
type/ownership/null/bounds behavior, gave only 0.16% in this run. Sampling alone
would have over-prioritized this change. Do not remove those checks on this evidence.

.NET's managed allocator normally advances an allocation pointer, while Unity's
configured Boehm collector uses its own allocation machinery. Their different GC
designs do not imply that Cilica must reproduce either collector to avoid a native
allocator call per short-lived string. See the primary
[.NET allocation description](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/fundamentals)
and [Unity 6000.3 GC description](https://docs.unity.cn/6000.3/Documentation/Manual/performance-incremental-garbage-collection.html).
The installed Unity 6000.3.2f1 source and retained generated C++ supply the exact
code comparison; they do not establish current Unity timings.

Dictionary inline storage remains worth investigating after the measured allocator
and field-access changes. It needs particular care around resize, reentrant mutable
key callbacks, free-slot reuse and reference clearing. Replacing its entries with
structs solely because .NET uses them is not yet an evaluated implementation.

## Correctness, review and next slice

All seven diagnostic variants match all 523 retained oracle observations in
release. The strongest combined variant also matches them in:

- O2 with the bounded pthread stack.
- O1 ASan/UBSan with forced collection and internal/borrow diagnostics off.
- O1 ASan/UBSan with forced collection and both diagnostics on.

The requested pthread stack is 512 KiB; actual size is checked in 512–576 KiB.
Maximum individual native frames are 432 bytes release and 336 bytes sanitized.
Final runs have no sanitizer diagnostics. With diagnostics on, the experimental
local-output bridge falls back; the pool and field-address changes remain active.
These tests cover this benchmark, not arbitrary allocation failure, instance
isolation, slab exhaustion or inherited-layout cases. No broad conformance suite
was rerun because production code is unchanged.

Review checked sample accounting (exclusive versus inclusive), fixed source
identity, allocator/collection counts, staged output writes, slab ownership and
destruction, cold fallbacks, timing isolation, and the field pointer/layout proof
still needed. Slabs must not become roots; only live inventory objects are traced.
ASan does not detect every stale access to a recycled slot whose slab stays alive.

The next production slice should:

1. Introduce bounded per-instance small-string storage with an explicit native
   reservation budget; retain collection, managed quotas, fresh live identities,
   allocation-failure origins, public handles and complete instance teardown.
2. Test retained/live strings through recycling, multiple instances, empty/one/
   multi-unit strings, UTF-16, exhaustion/failure recovery and diagnostic membership.
   Consider poisoning free slots in sanitizer builds.
3. Regenerate from the changed compiler, run targeted conformance plus the full
   benchmark transcript under forced GC/sanitizers, and remeasure release time
   and memory before committing the implementation.

Keep field-access and local-output proofs as separate subsequent slices so that
correctness and speed remain attributable.
